# Stage 1: Pod capture (raw truth)

## Purpose

Stage 1 records the raw inertial measurements generated by wearable IMU pods during a run. This stage exists to capture truth, not interpretation.

The output of this stage is the upstream truth source for the entire pipeline. Every downstream stage depends on the integrity of this raw capture. For this reason, Stage 1 must remain stable even as downstream algorithms evolve.

---

## What happens in this stage

During a run, each IMU pod measures motion and streams inertial data to a logger over BLE.

The logger:
- connects to all required pods
- receives timestamped accelerometer and gyroscope samples
- writes the raw streams to local storage continuously
- creates a dedicated run folder to contain the capture session
- stores minimal metadata to preserve provenance

The focus is to create a clean and complete run record that can be pulled to an analysis machine later without ambiguity.

---

## Inputs

Stage 1 does not consume data from upstream pipeline steps. Its primary inputs are the physical system itself:

- IMU pods mounted to the runner (thigh and calf configuration typically)
- BLE Central logger device
- user start and stop actions
- environmental conditions such as treadmill or outdoor running

---

## Outputs

The outputs of Stage 1 are raw artefacts and minimal metadata.

### Raw measurement streams
For each pod:
- accelerometer (3 axis)
- gyroscope (3 axis)
- timestamps or sequence counters sufficient to reconstruct time order

These outputs represent the raw sensor truth for that run.

### Capture metadata
Each run must include enough metadata to allow reliable interpretation downstream, including:

- run identifier
- capture start time and stop time
- pod identity list
- pod mapping information (which pod corresponds to which limb segment)
- firmware or version information where available
- warnings and fault notes (disconnects, dropouts, battery concerns)

---

## What this stage does not do

To avoid building on assumptions too early, Stage 1 intentionally avoids any biomechanical interpretation.

It does not include:
- filtering
- alignment
- event detection
- stride segmentation
- feature extraction
- cadence estimation
- cloud upload or app integration

This separation is deliberate. Interpretation belongs downstream where it can be validated using plotting tools and repeatability checks.

---

## Why this stage matters

Most downstream failures can be traced back to unstable capture behaviour. A simple rule applies:

If Stage 1 is inconsistent, no amount of downstream processing will make the results trustworthy.

Stage 1 therefore prioritises:

- completeness of recording
- repeatability across runs
- deterministic folder structure and output format
- visibility of failures

---

## Key design goals

### 1. Faithful capture
The logger should record what is received without modification. Any transformation applied at capture time makes it harder to validate later.

### 2. Deterministic artefacts
The same hardware and workflow must create run folders that follow the same rules every time. Downstream tooling depends on predictable structure.

### 3. Clear provenance
Every sample stream must remain traceable back to:
- the specific pod that generated it
- the physical limb segment where that pod was mounted
- the time window of the run

### 4. Visible failures
Disconnects, packet loss indicators, or unusual behaviour must be recorded and exposed in metadata. Silent failure is unacceptable.

---

## Quality considerations

This stage defines the baseline quality of the dataset. Common quality risks include:

- loose mounting causing motion between pod and limb
- inconsistent orientation or placement between runs
- BLE dropouts leading to missing segments
- unstable sampling behaviour
- battery depletion during capture

These are not analysis problems. They are capture integrity problems.

The purpose of metadata and logs is to ensure these issues can be identified later during validation.

---

## Acceptance criteria

Stage 1 is considered successful when:

- all required pods were recorded for the run
- the run folder is complete and well formed
- sample streams are monotonic in time order
- the capture log contains no unreported failures
- mapping metadata is present and unambiguous

If these conditions are not met, downstream processing may continue but the run should be treated as lower confidence until inspected.

---

## Relationship to downstream stages

Stage 1 feeds Stage 2 ingest, which copies the run into the canonical run structure and begins the formal pipeline.

Downstream stages assume:
- Stage 1 capture artefacts remain unchanged
- pod mapping metadata remains available
- raw streams are the ground truth reference for later validation and debugging

When questions arise later, the raw capture from Stage 1 is what everything is compared against.
